## 行为与保护

原问题有两层：共享 IndexedDB 缓存版本一变化就永久阻止其他标签保存；账号合并按整个任务比较，使重命名与输入等互不冲突的改动也产生冲突。仅移除警告或放宽 revision 会造成旧快照覆盖新内容。

现在本地缓存仍执行原子 CAS，但冲突后读取最新状态并重试三方合并。账号服务仍使用单调 revision CAS。每个文档在独立恢复记录中先保存自己的草稿，再参与共享缓存合并，刷新时从 sessionStorage 的恢复标识读回。IndexedDB 真正写入失败仍明确阻止不安全退出，不把保存失败伪装成成功。

合并以任务、稳定实体 ID 和可编辑字段为单位：

- 不同任务、同任务不同字段分别保留；文本中的可判定不重叠编辑自动合并；重叠改动保守保留双方完整内容。
- 真冲突保留远端原任务及确定 ID 的完整本地冲突副本，来源与字段记录在 `syncConflict`。不会自动跳到副本；状态面板可打开或保留为独立任务。其他任务继续保存。重复重试不会复制出多个相同副本。
- 删除用 `deleted` 墓碑同步。若另一个标签仍停留在被删任务，保持原任务位置并提供恢复；删除与编辑并发时额外保留编辑副本。
- 当前任务、PNG / SVG 路径、查看的结果版本与导航标记属于标签自己的视图；普通 / 专业模式、绘图设置和模型引用属于同步内容。同步不调用页面导航、focus 或滚动重置。
- 服务端返回的执行终态优先于迟到的运行中观察；结果以固定 ID 去重。接收回执归属原任务，失败的竞争提交不遮蔽已接收执行。接收时清空已提交要求属于派生变化，不覆盖同时准备的下一次草稿，也不恢复已经清空的旧输入。
- 同源使用 BroadcastChannel 与 storage 失效通知，广播只带缓存键 / 版本，不带内容。独立来源通过账号服务每 5 秒检查版本；恢复可见、focus、pageshow、online 自动追赶。
- 无变化的读取不 hydration / 上传。带固定 ID 的任务、执行、候选和版本集合以内容比较，避免列表排列差异导致上传循环。上传仍通过有界白名单，原文件与密钥不进入同步快照。

新生成 / 精修先持久化提交快照，网关核对 activeRunId / submitting 记录，沿用原子任务锁与 runId 幂等记录，在领取执行位后再次核验当前任务。已被其他页替换的提交不会发送到生成服务。同步与恢复查询本身不触发 createJob / refineImage；输入优化仍沿用独立执行标识和同一服务端任务锁。

## 共享接口

- `schema: 1` 不变。任务新增可选 `deleted: boolean`、`syncConflict: {taskId, fields}`，最多 40 条字段路径。
- `GET /api/workspace?revision=n`：相同版本返回 `{revision, unchanged:true}`，否则完整原响应；不带参数的老客户端仍得到完整响应。
- 原 PUT revision、活跃账号 / 会话、可信 Origin、X-Workspace-Account 和结果归属检查全部保留。
- 删除墓碑、冲突副本和新的 Web 合并逻辑需要两个域名配套更新。已打开的旧网页不会凭空获得新版算法；发布时需先妥善保留旧标签草稿，再完成客户端升级。
