## 1. 已实现的监控

| 层次 | 内容与口径 | 边界 |
|---|---|---|
| 准入与队列 | 全局运行/排队/预留槽及峰值；账号限制、IP 限制、队列满、停止准入、冻结账号分别计数；从预留到开始执行的等待时间 | 账号、IP 额度仍同时包含运行与排队，不在此轮改成新的排队协议 |
| 任务执行 | 执行开始/返回/抛错/领取失效/终态落库失败；整任务耗时直方图 | `execution.returned` 表示执行函数返回，不等价于业务成功；最终状态以 Mongo 任务记录为准 |
| 阶段 | 规划、参考分析/准备/选择、绘制、评审、样式；模型文本/图片、SVG 渲染、材料读取、阶段图片保存的耗时/错误 | 墙钟耗时包含模型等待，不能当 CPU 时间；固定类别，不输出提示词、账号、IP、任务 ID、密钥或签名 URL |
| 恢复日志 | 缓存命中、未知状态阻断、Retry-After 等待、检查点开始/完成/拒绝/等待/未知、日志写入失败 | `workflow.*` 包括嵌套检查点，不能解释为独立付费请求次数；`model.*` 为模型操作指标，也不替代供应商账单 |
| 材料子进程 | 活动数量与峰值、繁忙拒绝、完成/失败、耗时 | 保留原来的 2 槽、384 MiB Node 堆和 60 秒限制；不声称已采集每个子进程单独的 RSS 峰值 |
| Core 进程 | RSS/堆/外部内存、累计 CPU 时间、事件循环利用率/延迟 P95/最大值 | 事件循环为观测器生命周期窗口；计数、峰值和直方图在进程重启后重置，按 startedAt 分段计算 |
| Mongo | 缓存字节/上限、连接、驻留内存、读写排队、活动任务数量与最老任务年龄 | 15 秒缓存并合并并发采集，数据库查询限定 1 秒；权限不足明确返回 unavailable，不以零替代 |
| 三节点主机采样工具 | CPU ticks、可用内存/Swap、缺页/OOM、磁盘容量/inode/I/O、网卡字节/错误/丢弃、PSI | 连续样本才能算速率与趋势；虚拟网卡流量不能直接换算公网费用 |
| 容器与现有服务 | Docker 用量/限制/重启/OOM，Linux cgroup v2 节流/内存峰值；可选显式指定 systemd 代理/隧道单元状态及 Restart 策略 | 只读；不重启代理、不调整容器限制、不更改香港其他项目或新加坡服务 |

`GET /internal/operations` 默认关闭。启用须同时设置 `PAPERBANANA_OPERATIONS_ENABLED=true` 和独立的 `PAPERBANANA_OPERATIONS_TOKEN`（至少 32 字符，不能复用网关或管理员令牌）。请求头为 `X-Paperbanana-Operations-Token`。该凭据不能访问任务/API 管理操作；响应禁用缓存，不开放浏览器 CORS。两站公共 Gateway 不增加监控转发路由。

主机采样器是 `scripts/observe-node.py`，默认只采一条；可指定 60 秒间隔和有限样本数。每天一个权限受限 JSONL 文件，达到 100 MB 后停止写入，不自动删除旧文件。Core 未配置、Docker 不存在、权限不足均返回明确的不可用状态。Linux 受限容器已实际验证 `/proc` CPU、内存、磁盘、网络采集。

Core 保持内部网络：杭州可用 `--core-container <已核实的Core容器名>` 读取容器内 loopback 接口，令牌留在容器环境中，不出现在命令参数或输出中，不必发布新端口。另一方式是 `--core-url http://127.0.0.1:<端口>/internal/operations` 配合 0600 JSON 凭据文件（仅 `operationsToken` 字段）；拒绝非 loopback URL、URL 凭据及重定向。采集本身的短暂 Node/Docker 开销也需要计入线上观测。

**尚未执行的阶段 0 项目：** 三节点生产采集安装/启用、覆盖业务高峰和备份窗口的连续监控、告警接入、代理退出恢复演练，以及云控制台带宽 SKU/流量计费方式核实。当前交付的是已验证的采集能力与部署准备，不是已上线的持续监控。不会据本地假渠道耗时推算生产容量。

## 2. 同账号双任务的实证

隔离配置：

```dotenv
PAPERBANANA_MAX_ACTIVE_JOBS=2
PAPERBANANA_MAX_PENDING_JOBS=2
PAPERBANANA_MAX_JOBS_PER_OWNER=2
PAPERBANANA_MAX_JOBS_PER_IP=2
PAPERBANANA_CANDIDATE_CONCURRENCY=1
PAPERBANANA_SINGLE_REPLICA=true
```

这些值用于隔离验收和后续灰度建议，**没有修改生产值或默认值**。线上原有全局/账号/IP 的 1 槽限制不会因为本地测试而自动放开。候选数量与候选并发不同：每个验收任务生成 2 个候选，但每个任务同时只生成 1 个。

使用本机独立 Mongo 副本集（512 MiB、1 CPU、临时数据库），两个独立 Gateway 实例共享实际执行存储和同一个 Core。会话身份、模型响应、对象存储为隔离测试桩；工作区执行锁、真实 HTTP 路由、准入、规划/图片工作流和持久化恢复代码使用实际实现。清空继承环境，仅提供测试需要的变量；Node TCP/fetch 只允许 loopback，没有真实云密钥或模型调用。

发布基线副本的结果：

- 两任务分别使用不同 `taskId/runId/jobId`，同一账号经两个入口同时提交。
- Core 活动槽峰值 **2**，Mongo 同时存在 **2** 条 running 任务及执行记录。
- 图片测试桩两请求的执行区间实际重叠 **40 ms**；这是人为闸门控制的并发证明，不是速度基准。
- 每任务候选活动峰值 **1**；每任务产出 **2** 张图片，逐张比较对象字节和预期 SHA-256，A/B 内容不同且均归属正确。
- 先让 B 完成，A 仍为 running；不存在切换任务导致结果落入另一任务的问题。
- 不同账号共用同一 NAT、经不同入口也能同时完成；结果和 Mongo 所有者分别核对。
- 第三个同账号请求被账号限制拒绝；另一账号在同一已满 IP 上被 IP 限制拒绝，均没有模型调用。现有协议使用业务 `code=429`，并非所有路径都采用 HTTP 429。

## 3. 防重、故障与既有数据

12 个集成验收场景覆盖：

1. 同账号跨两个 Gateway 的两任务真实重叠。
2. 账号上限在模型调用前拒绝。
3. IP 上限与账号上限可区分。
4. 同一 run 重复提交不重复执行；A run 传入 B job ID 仍读取 A 的绑定结果；跨账号读取被拒绝。
5. 候选保持串行，乱序完成不串结果。
6. 不同账号同 NAT 的并行与所有权隔离。
7. 一任务图片调用结果未知后，其下一候选停止；刷新、重提、恢复及新 workflow 实例均不能重发，该图片请求始终 **1 次**；另一任务正常完成。
8. 明确拒绝后的恢复争抢只有一次成功，已完成的首个规划检查点复用，不重复调用；新增第二候选的规划仍正常执行。
9. 模型已返回后检查点写入失败保持未知，禁止自动重发。
10. Gateway 接收确认持久化失败返回 503，另一入口重提同一 run 返回冲突，不产生第二个 Core 任务。
11. 接收快照写入失败时，模型请求数为 **0**，预留槽释放。
12. 无关账号、已有任务及文件哨兵完全不变。

未知调用仍需核对供应商记录。测试证明的是程序没有自动重复提交；没有调用真实模型，不能据此宣称已经核验真实账单或供应商幂等收费承诺。

Gateway 丢失接收确认时，系统会保守保留“已接收但尚未确认”的执行锁。本轮没有新增自动匹配 job ID 或自动重新提交功能，避免以恢复体验换取重复收费风险。

额外修复：材料读取先检查并发、异步查找 Worker，再增加运行计数，原逻辑存在检查与占槽之间的竞争窗口。现已在异步查找后、占槽前再次检查。8 份并行文档请求的实测结果为 2 份执行、6 份明确繁忙；峰值 2、结束后槽数 0，后续请求仍可执行，文档内容未串用。
