# 邮箱验证手动确认补充修复

2026-09-08，承接用户对邮箱验证反馈修复的上线授权，修正用户尚未点击邮件按钮就显示验证成功的情况。

## 问题与证据

上线前的验证接口在收到 GET 请求时就完成验证。只读访问记录显示，注册受理后 4 秒已有一次验证链接请求，随后原注册页查询状态；稍后邮箱客户端又访问了同一链接。这支持“链接先被访问，旧接口因此执行验证”的解释，但无法确定第一次请求的实际发起程序，不能断言是 163 服务或某一浏览器的扫描器。

上一版修复了重复链接反馈和原注册页状态同步，没有阻止链接被提前访问时完成验证。本次补充修正这个触发条件。

## 本次行为

- 新邮件先打开第一方确认页，用户点击“确认验证邮箱”才发送验证请求。令牌通过 URL fragment 抵达页面，读取后移除地址栏片段，仅在页面内存保留到用户确认；不保存在本地存储。
- 旧邮件的 GET/HEAD 请求只跳转到确认页。打开页面、预览页面或执行页面脚本本身不完成验证。Better Auth 原验证路由禁用，避免绕过自定义处理。
- 实际验证使用来自受信任 Origin 的 JSON POST；保留原身份与邮箱绑定、注销屏障、有效期和幂等回执。验证不授予登录会话。
- 原注册页继续只读检查本次注册的状态；手动确认成功后自动更新。已有验证结果不批量重置。

## 验证与边界

Gateway 140、Web 353 项测试与 Web 构建通过。真实 Better Auth / Mongo 副本集覆盖 GET/HEAD 不消费令牌、未确认时登录拒绝、POST 并发验证、禁用路由别名、重复结果和同邮箱重注册隔离。Chrome 桌面与手机回归覆盖加载并执行确认页后仍等待、显式点击后原页面自动更新、无自动登录及重复打开链接。

本地邮件使用内存传输；没有发送真实邮件、创建生产测试账号或修改反馈用户的账号。生产浏览器使用不存在的测试令牌验证跳转、按钮和负面结果。未复现特定 163/微信客户端的真实预取程序。小程序上传与平台发布继续暂缓，无新增 env、数据库迁移或付费模型调用。
