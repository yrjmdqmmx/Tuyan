# 更新日志维护

公开数据源为 `apps/web/src/data/changelog.json`（schemaVersion 3），页面为 `/changelog`。仅展示已发布产品版本和已经发生的生态事件，无待发布区、搜索框或公告初稿来源标签。本次为本地修改，未部署。

## 独立版本与分类

| 分类 | 公共名称 | 编号规则 |
| --- | --- | --- |
| 官网工作台 | `Tuyan v3.7.1` | 独立三位版本号；PaperBanana 是 1.x–2.x 历史品牌，不开新产品线 |
| 排行榜 | `Tuyan Benchmark v2.5` | 独立两位版本号，不能复用工作台语义版本 |
| OpenAcad | `OpenAcad v1.1.0` | 独立三位版本号；与 Tuyan 分别升级 |
| 生态事件 | 日期及事件名 | Skill、MCP、小程序、平台上架不分配产品版本号 |

每条产品记录用 `product + version` 定义身份，在各产品内按数字版本倒序；稳定 DOM `id` 全局唯一。生态事件按日期倒序。分类入口顺序为“更新日志、图研工作台、Tuyan Benchmark、OpenAcad、生态事件”。无分类链接时默认打开“更新日志”汇总；其余入口单独筛选内容，并用选中样式及 aria-current 标识。现有网站导航、账户和手机“更多”交互不变。


## 汇总与分类视图

汇总由 `groupPublishedUpdates(data)` 直接使用相同的 `publishedVersions` / `publicEvents` 结果生成，不新增独立数据源，也不复制历史条目：

- 产品使用已核实 `release.date`，生态事件使用 `date`；没有有效发布日期的条目不会退回公告日或猜测日期。
- 所有公开条目按日期倒序，同日只有一个日期标题。日期相同时保留产品分类与该产品原版本顺序，再列生态事件，不推测具体发布时间。
- 每条产品显示分类、独立完整版本号及相同的新增／优化／修复正文；日期由所在日期组显示。生态事件在汇总中显示日期、类别和事件名称，原生态分类保留详情。
- 新记录只需维护原 JSON；汇总和分类自动同步。原数据、日期、版本号、发布状态、来源均不因视图改变而重写。
- `#all` / `#tuyan` / `#benchmark` / `#openacad` / `#ecosystem` 可分享分类，刷新、前进、后退保留选择；没有片段默认汇总。旧条目锚点仍解析到对应已公开记录。

## 公开数据与审计分离

- `entries` 只接收 `release.status: released` 且所有 `changes[].state: released` 的产品版本。所有 `surfaces` 必须是该条目已发布的端；小程序不混入 Tuyan 版本。
- `events` 没有 `version`，状态为 `recorded`。公告能够证明公告记录，但不能替代微信平台回执或 API 权限证明；仅有公告时，文案限“上线公告／上架公告”。
- `sources` 每项与 `changes[].sourceIds` 关联。公开且已核对的 Tuyan GitHub PR、提交、Actions 和固定提交文档可显示为链接。PR 或 commit 本身不能证明发布。
- `owner-confirmation` 只用于负责人明确确认的历史事实；`archive-record` 用于已经交叉核验的非公开发行资料。二者在审计文档中记录依据，无 URL，不在页面渲染来源标签。不能用这些类别绕过未完成的部署。
- 不公开私有仓库链接、机器路径、账号、密钥、运维地址。OpenAcad 的公开功能摘录和版本来自实际发行记录，私有证据的具体身份仅在维护审计保留。
- `announcementDate` 仅作来源核对，页面主日期使用 `release.date`。本轮负责人明确要求 Tuyan 3.0.0 按公告日期 2026-08-24 记录；不能由此改写为当天发生一次对应 SHA 部署。
- 1.0.0、1.1.0、1.3.0 的发布状态已由负责人明确确认，日期沿用公告。原 Git 证据缺口保留为历史审计，不再在公开页面标为未知。

详见[独立版本线审计](changelog-audit/2026-09-22-product-lines.md)。此前“全合并到工作台版本”的方案已被最新用户要求替代。[完整正文](changelog-audit/2026-09-22-version-log.md)由公开 JSON 导出，不作为第二份手动数据源。

## 后续追加

1. 复制[模板](changelog-entry.template.json)，选对产品；生态事件复制 `event` 模板。新内容先放维护草稿，只在实际发布后进入公开 JSON。版本号须由项目确定。
2. 逐项核对实际实现、版本归属和发布事实，合并同功能的提交；不要把内部目录、镜像或评测批次号当成产品版本。
3. 完成授权发布及对应端验收后，记录实际日期和来源，将最终发布范围写入 `entries`。仅更新日志页面上线不能证明配套模型渠道和后端思考参数已上线。
4. Tuyan 3.8.0 收尾时，仅移入其实际已发布工作台条目；核对并清理旧锚点，避免与 Benchmark／生态事件重复。不得为了展示草稿而只修改状态。
5. 有日期、版本或措辞差异时更新审计，再修正公开摘要。公开页只保留用户可感知内容与必要的能力边界。
6. 保留稳定 ID 和已有已发布条目的旧锚点。未发布的 3.8.0 旧链接不重定向到其他已发布版本，避免误导。
