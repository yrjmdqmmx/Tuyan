# 参考图上传额度核查与调整

核查日期：2026-09-10。分支：`codex/web-tokendance-defaults-nav-20260910`，基线 `b2bb1108447fc46b5be75578bcdca7fba39844db`。实现和验收均在隔离工作树；生产仍为 `2c518f97c06c3fc0149c299244c3489db232b531`，本轮没有发布、支付或真实供应商消费。

## 结论与先行方案

旧的“3 张、5MB”来自应用硬编码和环境变量，并非对象存储或 Nginx 的图片承载上限。先在会话中给出下表方案，再实施。采用原图上传与模型提交两个额度层次；表中的新值是经过验证的运行额度，不是声称测出了服务器的物理极限。

| 项目 | 原来 | 新平台上限 | 依据 |
| --- | --- | --- | --- |
| 生成参考图原文件数量 | 3 | 8；实际提交再取模型/工作流额度 | OSS 直传、逐张处理；已完成 8 张真实 HTTP 上传和下游调用参数验证 |
| PNG/JPEG/WebP 单文件 | 5 MiB，界面写成 MB | 20 MiB = 20,971,520 字节 | 直接传对象存储；Core 只同时处理一张，32MP 解码预算另行约束 |
| 原文件合计 | 无独立校验，间接最多 15 MiB | 80 MiB = 83,886,080 字节 | 控制每批存储、网络与处理时长；签名前、finalize、任务输入均校验 |
| 原图尺寸 | 精修已有 16,384px / 20MP；普通参考图缺少完整解码门槛 | 每边最多 16,384px、单图最多 32,000,000 像素；同时满足 | 真实容器解码试验与每次单张处理；拒绝损坏图、伪装格式和动画 |
| SVG | 5 MiB，通常固定栅格化至 1024px | 文件仍 5 MiB；尺寸同原图约束；按模型尺寸栅格化 | SVG 复杂度不能按压缩后的文件大小推断；文字需转为路径或导出 PNG |
| 精修来源数 | 单张 | 单张，原文件放宽至 20 MiB | 现有产品是单来源编辑；不把供应商多图编辑能力误当成已有功能 |
| 并发 | Web 同批 Promise.all；没有统一图片处理闸门 | Web 最多 2 个 PUT，小程序串行，Core 单进程最多 1 个图片处理；忙时 429 可重试 | 避免多个解码缓冲和大 PNG 同时堆积；保留当前单任务执行队列 |

新 Web 连接旧后端时仍按 3 张、5 MiB 校验。服务器若保留较低环境配置，注册表公开实际较低额度，界面不会宣传未启用的原图额度。

## 生产承载与链路

只读 SSH 核验及一次隔离探针，未更改生产服务或读取/输出密钥值：

| 项目 | 实测 / 配置 |
| --- | --- |
| 主机 | 4 CPU；内存约 14.84 GiB，可用约 11.74 GiB；Swap 4 GiB 空闲；磁盘剩余约 31 GiB |
| Core | 内存限额 3 GiB，CPU 1.5；观测 RSS/容器使用约 119 MiB |
| Gateway | 内存限额 512 MiB，CPU 0.5；观测约 101 MiB |
| Bench / Plot / Mongo | 内存限额分别 2 / 2 / 3.5 GiB；不能把主机全部剩余内存都给图片处理 |
| Core 任务入队 | active=1，pending=2，每 owner/IP=1；本轮不扩大付费任务并发 |
| 旧生产参考额度 | `PAPERBANANA_MAX_REFERENCE_IMAGES=3`、`PAPERBANANA_MAX_REFERENCE_BYTES=5242880` |
| JSON 请求体 | Nginx 1100k；Gateway 和 Core 均 1mb；原文件不经过该 JSON 请求体 |
| 超时 | Nginx read 900s / send 60s；Gateway 默认后端 15s；本轮 finalize 改为 40s |
| 图片处理 | Sharp 0.35.3，cache=false，concurrency=1；只启用 PNG/JPEG/WebP 解码器，单次 Sharp 操作超时 15s |
| 对象存储 | 服务端签名限定 Content-Type / Content-Length，客户端直接 PUT；Core 校验实际对象头和读取字节上限 |

真实调用链：

1. 客户端校验数量、文件大小、批次总量和尺寸 → Gateway 转发少量描述符 → Core 签名。
2. 文件直接 PUT 对象存储 → finalize 检查签名、owner、当前账号 lifecycle、对象实际元数据；精修会实际解码，SVG 会校验可安全渲染。
3. 普通生成：从原图重新派生模型输入。主模型能识图时进入主模型规划；独立识图时进入所选 vision 模型，分析文字再进入生成提示词。图片不会因为选择 Seedream 生图型号就自动成为 Seedream 的多图输入。
4. 修复了 vanilla + main_model 的遗漏：此前参考图准备后未实际进入该路径；现在明确识图并把分析放入最终生图提示词。
5. 精修 direct-edit：源图直接进入 image 模型。analyze-redraw：源图先进入 vision 模型，分析文字参与重绘。因此这两种精修必须使用不同的模型输入策略。
6. 精修继续创建独立原图快照，保持账号归属和历史任务隔离。派生图按策略摘要命名；每张写入后登记到任务，避免后续超限时失去清理线索。

### 资源试验的证据和边界

生产主机使用现有 Core 镜像启动一次性容器，`--network none --read-only --memory768m --cpus.5 --rm`，不注入业务环境和凭据。结果保存在 [server-decoder.jsonl](server-decoder.jsonl)：

- 8000×4000 科研风格平色图（32MP）缩至 4096×2048：322ms，最大 RSS 109,428 KiB。
- 4096×4096 噪声 JPEG：输入 14,682,758 字节，转无损 PNG 后 48,939,520 字节；2632ms，最大 RSS 278,308 KiB。
- 第二项证明“上传 20 MiB”和“模型允许 20MB”不能直接等同。PNG 转换可能扩大文件，处理后必须重新检查单图与合计字节。

这是资源余量样本，不是生产流量压测，不证明任意 32MP 图的最坏耗时。保留 Core 单处理闸门、原图像素上限和 Sharp 超时。SVG WASM 渲染本身没有可中断的同等超时，故保留 5 MiB，不随栅格图一起放宽。

## 图片处理与界面

- 总是从原文件派生，切换模型不会反复缩放上一次处理后的图片；原文件保留。
- 校正 EXIF 方向；符合模型格式、无需旋转缩放的 JPEG/WebP 保持原字节。其他情况优先无损 PNG，不自动降低 JPEG quality；有损缩放是必要的等比重采样，界面明确给出目标边长和像素预算。
- 只在超出所选策略尺寸时缩小，不放大小图，不自动裁剪；缩小后仍检查最小短边。无损输出单图/合计超限时中止，提示用户裁剪、自己压缩或换模型。
- SVG 保留 5MiB，检查安全引用、viewBox/尺寸；生产 Core 没有字体文件，带未转曲文字的 SVG 明确拒绝，以免静默丢标签。路径型 SVG 按模型预算渲染，不再统一降为 1024px。
- UI 显示当前真正读图的型号、平台原图额度、模型提交数量；详细处理规则可展开。选择更严格型号后保留已有图片，显示如何处理，禁止带着冲突继续提交。
- 小程序改用原图选择，补齐合计/像素校验、共享目录字段和动态提示，保持串行 PUT，上传超时延长到 120s；精修任务结果入口按 direct-edit / analyze-redraw 显示真正消费者规则。
- 旧后端兼容：没有 v2 声明时按旧 3/5MiB 处理，不承诺新处理能力。

## 上线时的配置要求

本轮仅修改部署脚本默认值，不修改线上密钥文件。已有运行环境不会因重建镜像自动从 3/5MiB 变为新额度。正式发布时应在保留现有其他配置的前提下设置：

```dotenv
PAPERBANANA_MAX_REFERENCE_IMAGES=8
PAPERBANANA_MAX_REFERENCE_BYTES=20971520
PAPERBANANA_MAX_REFERENCE_TOTAL_BYTES=83886080
```
